# NTE 的 Adreno 移动渲染优化：GDC 2026 分享总结

- 原讨论日期：2026-10-24
- 归档日期：2026-10-28

> 历史讨论归档：保留原报告的技术结论、公开参考链接与证据限制。设备、驱动、引擎支持及资料访问状态均以原讨论日期为准，本次未重新核验；不代表新的实测、完整源码审计或对所有录像的完整观看。

这场 NTE（《异环》）分享的核心，不是“把几个 Shader 改快”，而是围绕 Adreno 重组 UE5 的数据流、可见性处理和帧生成方式。

本报告按当时官方录像中可核对的章节与字幕整理，原理部分用官方技术文档补充。先说明边界：没有拿到完整逐字稿，部分幻灯片和自动字幕里的性能数字无法可靠核验，因此下面不引用那些提升百分比，也不猜测试基线。

[官方完整录像，约 45 分钟](https://www.youtube.com/watch?v=jogymfpx7uk)

## 一、整体思路：从五个方向减少成本

这场分享可以串成一条线：

- Tile Memory Heap：中间数据少往返系统内存。
- 定制 Mobile Deferred：调整 Render Pass 和资源使用方式，让片上驻留真正发挥作用。
- AFME2：部分显示帧通过生成得到，减少完整重绘的负担。
- SGSR2：真实帧先以较低分辨率渲染，再重建输出。
- SDOC＋SAGC：前者减少无效绘制，后者根据设备运行状态调整负载。

其中最值得深入的两块，是片上内存／管线改造，以及软件遮挡剔除。后者在录像里占了很长一段，并不是附带提一下。

## 二、为什么 NTE 会遇到这些瓶颈？约 05:17 起

讲者描述的是密集城市开放世界：远距离可见场景、高速移动、战斗反馈、动态光照和高分辨率输出，同时存在。

这会同时带来几类压力：
- 模块建筑和大量物体增加可见性判断、提交及几何处理成本。
- 高分辨率的中间渲染目标增加数据读写量。
- 多个渲染阶段反复消费颜色、深度、运动矢量等数据。
- 手机还必须控制持续功耗，不能只追求冷机时的最高 FPS。

所以它不是纯粹的“ALU 太多”或“带宽太高”问题，而是需要沿着整帧的数据和工作流逐项处理。[官方议程](https://attend.gdcevents.gdconf.com/event/gdc-festival-of-gaming-2026/planning/UGxhbm5pbmdfNDMzMTE1Nw%3D%3D)

## 三、Tile Memory Heap：真正重点是资源放在哪里。约 07:32 起

先把两件事区分开。

普通移动端分块渲染，会尽量把一个 tile 内的中间结果留在片上。例如几何与光照组织成兼容的 subpass，就可能省掉 GBuffer 的外部写回和重读。

但这不等于后续所有阶段都能一直复用这些片上数据。跨阶段的资源需求、Render Pass 切分、提交边界等，都可能使数据仍需保存到系统内存。

Tile Memory Heap 则进一步把片上内存以可显式管理的内存堆形式开放给应用，让选定资源能在允许的范围内跨 Render／Compute Pass 使用。

NTE 录像中明确提到的资源包括：
- SceneColor。
- Velocity。
- SceneDepth。

因此，这场不能只概括成“把 GBuffer 放在片上”。更重要的是让颜色、深度、运动矢量等被后续阶段使用的关键资源，尽量避免重复往返系统内存。

可以用一个原理例子理解，但这不是 NTE 的实际 Pass 清单：

原来，阶段 A 生成数据后写到系统内存，阶段 B 再读回来；之后阶段 C 又读取它。改造后，在容量、访问方式和生命周期允许时，几个阶段直接消费片上数据。

省掉的是其中的搬运，而不是凭空消除了这些阶段的算法计算。[高通 Tile Memory Heap 技术说明](https://www.qualcomm.com/developer/blog/2026/05/high-performance-memory-extension-optimize-memory)

这里还有一个非常重要的限制：它不是跨帧永久缓存。扩展对资源内容的有效范围、命令缓冲绑定和提交边界都有约束；默认有效范围是一个 command-buffer submission batch，只有具备相应能力时才扩大到一次 queue submit。NTE 也提到了提交组织对集成的影响。

所以这不是“分配到一个更快的 heap，然后什么都不用改”。引擎需要一起处理资源寿命、同步、别名复用和提交组织。[Khronos 扩展说明](https://docs.vulkan.org/features/latest/features/proposals/VK_QCOM_tile_memory_heap.html)

## 四、定制 Mobile Deferred：不是只切一个项目设置。约 13:45 起

讲者把这条改造后的路径称为 one-pass mobile deferred，并说明让关键资源在后续处理阶段继续留在片上。

这里不要把 one-pass 理解为“整帧所有工作只有一次 draw，甚至没有后处理”。更稳妥的理解是：他们重新组织了移动延迟渲染及其数据消费方式，减少中间结果反复落到系统内存的必要性。

这与 Forward／Deferred 的取舍直接相关：

- 不能只数 Deferred 有几个 GBuffer，就判定它一定更耗外部带宽。
- 也不能只看到使用了 tile memory，就认为后续 Pass 的访存都免费。
- 最终要看资源的生产者、消费者，以及中间是否发生实际保存和重读。

录像展示了繁重城市场景中的验证，讲者报告相关冗余主存读取明显减少。但具体字节数及百分比的字幕存在歧义，因此不将它们列为可靠数据。

可借鉴的思路是：比“这个 Shader 能不能再少几条指令”更上层的一个问题，是“这个中间结果为什么要出片、又被读回来？”

## 五、AFME2：困难不只在生成帧，而在处理失败区域。约 16:00 起

这部分讨论通过帧生成降低完整渲染的负担，兼顾显示流畅度和持续功耗。

需要分清三个量：
- 游戏逻辑更新率。
- 真正执行完整渲染的帧率。
- 最终显示给玩家的帧率。

生成更多显示帧，不等于逻辑更新、真实渲染和输入响应也同比提高。

NTE 这部分比较有价值的工程细节，是对伪影的处理：

不连续、不规则运动容易导致生成错误，讲者举到了高速旋转车轮等情况。团队在 Velocity Pass 中增加了一张 R8 mask，用来标记有问题的对象／区域，针对性处理这些插帧困难情况。

当时仅确认到“额外 R8 标记纹理”和它的用途，不能进一步断言这些区域一定采用单独重绘，或具体按什么粒度禁用生成，字幕没有清楚支持这些细节。

他们还提到通过 UE5 自定义 hooks 和平台特定 Shader 接入，兼容已有后处理，并避免影响 PC／主机路径。

可借鉴的点：帧生成不是简单接一个 SDK，而要让运动数据、异常区域标记和现有渲染管线协同工作。高显示帧率之外，还必须单独检查伪影与响应。[录像对应部分](https://www.youtube.com/watch?v=jogymfpx7uk&t=960s)

## 六、SGSR2：真实帧少渲染一些像素，再做时序重建。约 22:45 起

SGSR2 与 AFME2 解决的不是同一个问题：

- SGSR2 主要降低每个真实帧的内部渲染分辨率成本。
- AFME2 主要处理真实帧之间的显示帧生成。

根据高通官方实现，SGSR2 使用低分辨率颜色、深度、运动矢量和历史信息进行时序超分；不是简单放大图片，也不是 VRS，更不能直接叫成 NPU 神经网络超分。

NTE 讲到的适配重点包括：
- 两遍／三遍执行路径的选择。
- FP16。
- 按设备档位和场景复杂度配置策略。
- 不只关注重建耗时，也比较带宽表现。

讲者还强调跨平台使用，而不是只依赖某一种 Snapdragon 专用硬件。实际落地仍要核对 API 与设备能力。

从集成原理看，运动矢量、jitter、历史重置、曝光和镜头切换都会影响时序重建效果。这些是官方实现的通用要求，不代表已经核实 NTE 每一项如何处理。

录像里的内部渲染比例及对比基线名称有误识别，所以这里不填具体数值。[SGSR2 官方实现与说明](https://github.com/SnapdragonGameStudios/snapdragon-gsr/blob/main/sgsr/v2/README.md)

## 七、SDOC：这场最值得借鉴的架构取舍。约 26:27 起

SDOC 是 Snapdragon 优化的软件遮挡剔除。基本思路是在 CPU 上用简化的场景遮挡表示，提前判断哪些对象不需要交给 GPU 绘制。

### 1）为什么考虑替换硬件遮挡查询？

硬件查询由 GPU 判断，但 CPU 如果要根据结果决定后续提交，就会遇到结果何时可用的问题。在他们的实现中，这种 GPU→CPU 依赖可能造成流水线气泡或不稳定。

这不是说所有硬件查询都会立刻 stall，而是查询组织、结果消费时机和平台会决定实际成本。

软件方案可以减少对 GPU 查询结果的依赖，但必须支付 CPU 光栅化、查询及场景管理成本。因此它不是免费把 GPU 工作删掉，而是进行一次工作转移与整体优化。

### 2）NTE 的城市资产，为什么反而不好剔？

他们大量使用模块化、实例化的小块几何来构建城市。这对内容复用与 GPU 绘制组织很有价值，但对软件遮挡并不天然友好。

软件遮挡更喜欢大而简单的遮挡体，例如一栋建筑外轮廓的简化代理。若把大量小模块逐一软件光栅化，CPU 成本可能高得超过省下的 GPU 工作。

于是出现两难：
- 处理足够多遮挡体：剔除效果好，但 CPU 太贵。
- 提前停止、限制遮挡体数量：CPU 可控，却漏掉更多可剔除对象，GPU 工作又增加。

### 3）他们怎么改？

录像提到的改造包括：
- 改进遮挡场景及遮挡体管理，避免每帧完整遍历整个场景。
- 使用 ECS 式的数据组织，追求线性内存访问、减少虚函数调用。
- 将模块建筑、道路等碎片几何组织为更大、更简单的遮挡代理。
- 配合 SDOC 的 SIMD、缓存友好等实现优化。

其中 Snapdragon 的 NEON 优化也能在官方工具资料中得到确认。[SDOC 官方实现](https://github.com/SnapdragonGameStudios/snapdragon-oc)

### 4）真正结论是什么？

不是“软件遮挡一定比硬件遮挡快”。讲者的结论更接近：选型应该尽早与资产组织、场景管理和渲染架构一起决定。

同一栋楼，渲染用的模块划分，未必就是遮挡用的最佳划分。只换算法、不调整数据和代理表示，可能根本拿不到预期收益。

这点比某个单次测试快多少更有参考价值。[SDOC 讨论与结论](https://www.youtube.com/watch?v=jogymfpx7uk&t=1587s)

## 八、SAGC：把优化收益变成长期稳定表现。约 40:25 起

录像中，这部分不是“让系统神奇地自动调好一切”。它涉及查询 CPU／GPU 利用率、温度状态等信息，再由游戏逻辑决定如何调整分辨率、FPS、粒子密度等负载。

讲者也提到初始化、运行、关闭的集成生命周期，以及运行时批量查询信息的方式。

可以把它理解为：
- 前面的技术减少单帧成本或完整渲染负担。
- 这一层根据设备实际状态，决定节省下来的预算用于画质、帧率还是功耗控制。

因此验收目标不是只看刚启动时的 FPS，而是看持续运行后的帧时间、功耗、温度及画质是否稳定。[录像对应部分](https://www.youtube.com/watch?v=jogymfpx7uk&t=2425s)

## 九、核心结论与比较方法

1. 带宽优化不只是少采样贴图。
改变 SceneColor、Depth、Velocity 的存放位置和使用链路，也可能减少大量外部往返，而 Shader 的数学运算未必有同等幅度变化。

2. 不能用这一场证明“带宽永远比 ALU 重要”。
它说明的是 NTE 在特定平台和场景里，找到了值得处理的数据流成本。其他场景若从 ALU 优化中得到更大收益，并不与此矛盾。

3. 不要把不同技术的收益简单相加。
SGSR2 降低分辨率后，渲染目标流量本来就变小；此时再用 Tile Memory Heap，绝对节省量会与原生分辨率不同。帧生成也会改变单位时间真正渲染的帧数。

4. 剔除优化与内容管线必须一起设计。
最有价值的经验之一，是专门为可见性判断建立合适的数据和遮挡代理，而不是直接复用全部渲染几何。

5. 比较时分开记录“真实渲染帧率”和“显示帧率”。
否则插帧后的 60 FPS、原生渲染 60 FPS，以及相同画质下的功率数据，很容易被混成一组无法比较的结果。

一句话概括这场：让看不见的对象少提交，让中间结果少搬运，让真实帧少渲染一些像素，再通过帧生成和运行状态反馈，维持手机长期游戏时的表现。这是报告的归纳，不是讲者原话。
